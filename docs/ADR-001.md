# ADR-001 — Local M1 API, immutable content and shared rendering

Date: 2026-10-11. Task: `CMS-M1-00`.

## Status

Accepted as the implementation contract within the user's **Approved CMS-001 v2 — M1 local/emulators**, recorded in the [approval register](../../approvals/APPROVAL-REGISTER.json). M1 is open. This ADR refines the [frozen architecture](../../docs/CMS-ARCHITECTURE.md) and allowlist, not the historical handoff's hash or scope. It does not authorize M2–M4, local acceptance or deployment.

**Verified:** stack, six required endpoints, single-role policy and local boundary were selected in the approved bundle. **Proposed implementation:** source contracts and tests will implement the refinements below. **Unknown / NOT_RUN:** exact package/tool patches, runtime/emulator/browser results and compliance with test oracles await the Medium workers.

## Context

The public site is an HTML/CSS/vanilla-JavaScript baseline. It has no CMS backend. M1 must prove member login → Hero/SEO edit → revision save → private preview → immutable submission/review while preserving that baseline. The runtime must work without a real Firebase account or cloud resources. A token alone must not authorize content, and a reviewed revision must not change when an editor saves again.

The approved task size/file ownership and frozen allowlist constrain implementation. A second API framework, transpilation toolchain, upload workflow or release publisher would add scope without proving the M1 path.

## Decision

1. Use vanilla ESM `.mjs` + JSDoc, Zod boundary schemas, Vite admin tooling, Node22 ≥22.12 and one npm workspace/root lockfile. Setup pins exact releases and records Node/npm/JDK21+/CLI/emulator compatibility in `docs/DEPENDENCIES.md`. Dependency scripts remain disabled before source/audit review. This ADR does not claim those checks have run.
2. Use Firebase v2 HTTP `onRequest` function `cmsApi` in the guarded Functions emulator. Keep six REST routes at `/api/cms`: session GET; home draft GET/PATCH; snapshots POST/GET by ID; reviews POST. The Vite loopback proxy supplies same-origin admin requests. No Express framework or callable adapter.
3. Use `demo-pinky-lamb-cms` and required loopback Auth/Firestore/Functions/Hosting emulators. Validate config before SDK initialization; no ADC/service accounts/cloud fallback. Root historical `firebase.json`, `dist/`, references and vendor remain unchanged; local config is `infra-local/`.
4. Keep browser Auth in memory. Every API request verifies the emulator token, current Auth user, matching UID/email active verified membership and exact action. EDITOR/OWNER save and submit; REVIEWER/OWNER review; PUBLISHER reads only through API in M1. Reject self-review for every role, including OWNER. Browser/direct SDK Firestore reads and writes deny for all roles, including own membership reads. Server SDK authorization is explicit because it bypasses Rules.
5. Store one bounded `cmsDrafts/home` envelope for Hero/SEO. Firestore rejects the domain's nested heading arrays, so Draft and Snapshot persistence replaces only `content` with private `contentJson:string`; domain, HTTP, fixture and renderer contracts retain the original exact content object. Strict decode/validation precedes every use; no raw contentJson reaches HTTP. Shared codec lives in the allowed contracts/draft.mjs and snapshot handling reuses it. Canonical hashes use decoded content. PATCH replaces complete hero and/or seo objects; expectedRevision prevents silent overwrite. Bound input to64KiB and both decoded and actual persisted envelopes to256KiB, including JSON escaping/metadata/manifest. No copy-field queries or extra source files are introduced. Unknown keys and arbitrary layout/URLs are rejected. Existing `Heading`, `TextRun`, `Action` and `AssetUse` notation remains intact. The first draft seed was rejected before commit; no valid draft migration is required. See [Firestore supported data types](https://firebase.google.com/docs/firestore/manage-data/data-types).
6. Use one atomic transaction for each keyed mutation, including effect, audit and completed idempotency response. Same keyed payload replays; changed payload fails. Keep key records for the local fixture dataset lifetime. Firestore transaction callbacks have no external effects and stable IDs across retries.
7. Capture immutable Snapshot content and resolved legacy media/provenance manifest. Content hash binds canonical content, mediaManifestHash, schemaVersion and templateVersion. Current decision lives in `cmsReviewStates`, with an expected review revision. Append-only Review binds exact snapshot hash. Draft editing never mutates a submitted snapshot. M1 has no cancellation, local publication or release pointer.
8. Use one pure Hero/SEO renderer for private preview and filesystem QA export. Public projection excludes private member/source/review data. Preview has script-free sandbox containment and clears on logout. QA export preserves baseline public interactions while replacing Hero/static SEO and local system URLs. Export writes only the designated isolated output, never baseline, and invokes no Firebase/Hosting API.
9. Keep the full legacy catalog private server/exporter input. The existing authenticated GET draft route returns `DraftRead`, extending the persisted Draft fields with a response-only sanitized `catalog` array; it adds no endpoint or write field. Only ID/kind/status/public legacyPath/label/dimensions/duration reach the picker. Vite denies `.local/`, server/private source and the full catalog even through `/@fs/`; browser-safe modules never import the full catalog into the admin build. API projection and dev-file/build boundaries require separate checks.
10. Use explicit launcher and API-server guard modes for the actual Functions emulator environment. The launcher requires all configured project/host variables. The server requires exact demo GCLOUD project, Auth/Firestore hosts and the same fixed four-emulator config; any optional project/Functions/Hosting aliases must match. It installs a Node network fence independently before SDK imports. Three source/hash/version-pinned CLI tooling seams suppress only ADC environment discovery, supply the supported projectDir option for the exact isolated config, and replace runtime registry version lookup with setup-verified installed Functions SDK7.4.0. Original Auth/config/path checks and SDK minimum-version checks remain. Hosting's config-directory cwd requires an in-memory `../public-baseline` projection derived from Config.path and checked against the fixed baseline realpath; no source config or arbitrary traversal is allowed. XDG paths stay isolated, HOME and installed package bytes stay unchanged. Hosting uses approved alternate loopback port5010. CLI automatically starts loopback Eventarc9299 and Tasks9499 as Functions tooling companions; they introduce no CMS handlers or product operations. Report those companions and hub/logging/Firestore websocket auxiliaries with the four required services. The Node fence is not an operating-system firewall or proof of Java egress confinement.

Exact fields, HTTP errors, transaction order, hash definition, renderer interfaces and test oracles are normative in [SPEC-cms-identity](SPEC-cms-identity.md) and [SPEC-cms-content](SPEC-cms-content.md). Contracts stay inside the approved files; conceptual interfaces are not permission to add source files.

For the installed Google SDK metadata detection path, set supported `METADATA_SERVER_DETECTION='none'` in the guarded launcher and independently in the API before SDK imports. Source inspection confirms isAvailable returns false before its metadata request path. This avoids cloud availability probing while keeping Auth verification, explicit demo initialization and the network fence unchanged. It is not an ADC credential or a claim that every SDK method is network-free; actual emulator integration remains necessary.

11. Preserve the API's safe JSON transport errors despite the installed emulator's early32MiB JSON parser. Source/version/hash-check the exact cmsApi HTTP runtime and its resolved body-parser1.20.8; replace only its known first JSON factory with bounded raw collection (65536bytes, all body types, inflatefalse, original rawBodySaver). Keep other parsers/processes original. Return safe400/413 from raw-parser errors; the CMS still checks Auth/action, content type, strict UTF8/JSON and schema. Unsupported compressed transport returns400; unsupported mutation content type/charset returns415. Original runtime loads the application before middleware registration, so the reviewed configurable factory export is the minimal local seam. No node_modules edit, new framework/source file or verifier change is needed. Exact process/factory checks and required actual transport tests are in SPEC-cms-content. This fourth tooling adapter is an emulator compatibility detail, not a production transport design.

## Alternatives considered

| Alternative | Benefit | Reason rejected for M1 |
| --- | --- | --- |
| Browser writes private Firestore directly | Fewer API handlers | Rules cannot substitute for the selected trusted transaction/audit boundary; conflicts with approved direct-write denial |
| Callable functions or standalone Express | Existing convenience APIs | Approved transport is v2 HTTP REST; two adapters add contract drift and setup scope |
| Full SiteContent editor or generic page builder immediately | Broad content control | M1 proves Hero/SEO; full-site schema/template editing belongs to separately approved M2 |
| Mutable snapshot or draft pointer as review target | Less copied metadata | Later edits would alter the review target and break exact-hash approval |
| Last-write-wins or process-memory retry cache | Small implementation | Concurrent saves/retries can overwrite or duplicate effects; state must commit with Firestore mutation |
| Session cookie plus localStorage ID token fallback | Session persistence | M1 selects explicit memory tokens; another adapter and fallback add session/CSRF scope |
| Real Firebase project or Hosting preview channel | Remote sharing | Violates demo+loopback boundary and introduces cloud/account/deployment requirements |

## Consequences and limits

The bounded single draft allows atomic save/submission without partial edits. It limits size and future schema growth; a split document model needs a separately reviewed migration. The stable retry record stores response data privately until fixture reset; public projection never exports that record.

In-memory Auth requires login after reload. The private iframe preview cannot exercise baseline interactive scripts; the QA artifact verifies those scripts separately. A local snapshot fixture and successful export are not editorial approval evidence. The real submit/review workflow must be tested against the emulators.

Rules and API require separate tests because the Admin SDK bypasses Rules. Unsigned emulator tokens and loopback HTTP are local test conditions, not a production authentication/security design. No cloud readiness, legal certification or performance SLO is claimed.
